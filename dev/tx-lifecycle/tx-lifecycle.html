What linger.ms Does

The Kafka producer batches messages before sending to the broker.

linger.ms = 0
msg arrives
↓
I/O cycle completes
↓
sent immediately
no artificial delay
linger.ms = 5
msg arrives
↓
wait up to 5ms
↓
send entire buffer
as one batch
better throughput under load

The intent: accumulate multiple messages and amortise the network round-trip cost.

Why linger.ms=5 Hurts — Serial

Each commit blocks until ack. Next send can't start until ack arrives.

linger.ms = 5 (serial)
send(1) [5ms][ack] ── send(2) [5ms][ack] ── send(3) [5ms][ack] ── ...
total wasted: N × 5ms
linger.ms = 0 (serial)
send(1) [ack] ── send(2) [ack] ── send(3) [ack] ── ...
no wasted time — sends whenever ready

5000 serial commits × 5ms = 25 seconds of artificial waiting, before any real network time.

Still Hurts in Async Mode

appendMessageBlocking calls producer.send() then parks until the Kafka callback fires. The next commit can't start until it returns.

COMMIT₁: send(msg₁) → await(ack₁) → return txId₁
COMMIT₂: send(msg₂) → await(ack₂) → return txId₂
COMMIT₃: send(msg₃) → await(ack₃) → return txId₃
Only one message in the producer buffer at a time.
Batching never happens. linger.ms=5 is pure latency penalty.

When Batching Works — Multiple Connections

Concurrent threads share the same producer. Sends overlap in the buffer.

Thread A:
send(msg₁)
─────────────
await(ack)
──

────
send(msg₂)

await(ack)

──────
await(ack)

↓
Producer buffer: [msg₁, msg₂, msg₃]
↓
One batched network request

With 50 threads the 5ms cost is mostly absorbed — matches linger.ms=0 throughput.

Async serial: 5ms linger × 5000 sends = 25s of artificial delay alone. Network round-trip adds the rest.

What Would Need to Change

To decouple the send from the ack wait, we need a fire-and-forget send path.

Current:
send(msg) → await(ack) → [have txId] → await(indexer)
Proposed:
send(msg, correlationId) → return immediately → ... later ... → await(indexer, correlationId)
Problem: txId IS the Kafka offset.
We don't know it until the broker acks.
Need a correlation mechanism that maps correlationId → txId after ack.

This requires changes to the Log interface and the indexer subscription model.

Recommendation

Do now
  • linger.ms=0 is correct for current architecture
  • Concurrent connections already batch naturally at the producer
  • No regression for multi-connection workloads
To revisit later
  • Correlation IDs to decouple send from await
  • Changes to Log interface
  • Fire-and-forget in appendMessage
  • Then linger.ms=5 would help single-connection throughput
TL;DR: The batching benefit of linger.ms requires concurrent senders. With serial commits and a blocking send-await loop, linger only adds latency.
